description: Landing an approved proposal whose lines are written in a file, into a belief repository, by numbered steps with a check on each.
dependencies: []
---

A proposal is landed only when its lines are written in a source file, the living has approved it, and the order names the file and the repository. Work the steps in order. A step whose check fails, or whose wording calls for a judgment, is the stop point: change nothing more, and ask `{ Psyche core Sonnet }` one question that names the step, the file and what you saw. Sonnet answers it, or takes it to `{ Psyche core Opus }` when it needs a judgment the file and the module do not give.

1. Read the source file whole, and its edits file where the source says it uses one. List each target module, whether it is new, and each proposal's numbered lines. Check: every target module path is under `vision/`, `intent/`, `spirit/` or `knowledge/` of the one repository the order names, and every module a proposal names is one the order names.

2. Make the repository current. `git -C <repository> fetch origin`, then `git status --short` and `git branch --show-current`. Check: the branch is main, the tree is clean, `git pull --ff-only origin main` is a fast-forward, and `git rev-list --left-right --count main...origin/main` is then `0 0`. The tree moves only by that fast-forward pull.

3. For each existing target module, read it whole. Check: every old line the proposal removes or replaces (a `-` line, the left side of a `[-…-][+…+]`, a `from:` text) occurs in the file exactly once, character for character. A line missing or occurring twice is a question: the module has changed since the proposal was written.

4. Apply the proposal as written. A `+` line is the wanted line without its first two characters; a `-` line leaves; a bare line is unchanged; a `move` takes its text from the `from` module to the `to` module with the marked changes made. A new module is a file with front matter, a `description:` taken from the proposal's `::: description` and `dependencies: []` unless the proposal names them, then a blank line, then the body. Every fence stays as written, its language word included, and every line stays as written.

5. Register each new module in `modules.datom`, one entry in the form of its neighbours, `{ { <Kind> <name> Single.<N> } «<kind>/<name>/<N>.md» }`, placed in alphabetical order of the name. A module that holds two versions is `Span.{ A B }`. Check: every path in `modules.datom` exists as a file, and every new module file begins with `---` and a `description:` line.

6. Check the diff against the proposal. Check: `git diff --stat` names only the target modules and `modules.datom`, and the proposal's `+` and `-` lines per module, counted, agree with the added and removed lines of `git diff`, each added line a `+` line of the proposal and each removed line a `-` line.

7. Commit and push. One commit, the message `<module path>: <what changed> (<proposal name>, approved by the living)` and the attribution lines the harness gives for commits. Then `git push origin main`, unforced. Check: `git ls-remote origin refs/heads/main` equals `git log -1 --format=%H`. A rejected push is a stop point.

8. Bind what the proposal says to bind. A new module is bound to a permaflow only when the order names the permaflows or the module they sit beside; then `flow-meta 'Configure.Amend.{ <Address> Add.PromptModule.<module> }'` for each, a readback by `flow-meta 'Configuration'` counting the module, and the same entries in goldragon-persona `metaflows-0533.datom`, in one commit. Check: the live count and the declared count agree, or the order's known difference is named. A refusal such as `CurriculumUnavailable` is a stop point.

9. Tell the page. When the proposal was published as a page, order `{ Psyche core Haiku }` itself, or the publisher the order names, to retitle it in place, title alone, beginning `Purified` when every proposal landed and `Partly purified` when some did not; the page is neither rebuilt nor rechecked. When every proposal landed, the page is ruled: the same order tells `{ Psyche core Haiku }` to stop its watch and remove its entry from the open-books record.

10. Report Done to the sender of the order: the commit hash, the repository, the modules changed or created, the live and declared counts when step 8 ran, and what was not done. Skills regenerate on their own schedule; say that no flow reads the new text as a skill until they have.
