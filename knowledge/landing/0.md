---
description: Landing an approved proposal whose lines are written in a file, into a belief repository, by numbered steps with a check on each.
dependencies: []
---

A proposal is landed only when its lines are written in a source file, the living has approved it, and the order names the file and the repository. Work the steps in order. A step whose check fails is the stop point: do nothing further, change nothing more, and ask `{ Psyche core Sonnet }` one question that names the step, the file and what you saw. Sonnet answers it, or takes it to `{ Psyche core Opus }` when it needs a judgment the file and the module do not give.

1. Read the source file whole, and its edits file where the source says it uses one. List each target module, whether it is new, and each proposal's numbered lines. Check: every target module path is under `vision/`, `intent/`, `spirit/` or `knowledge/` of one repository, named in the order. Stop if a path is elsewhere or a proposal names a module the order does not.

2. Make the repository current. `git -C <repository> fetch origin`, then `git status --short` and `git branch --show-current`. Check: the branch is main, the tree is clean, and `git rev-list --left-right --count main...origin/main` is `0 0` after `git pull --ff-only origin main`. Never `git pull --rebase`, never reset. Stop if the tree is not clean, the branch is not main, or the pull is not a fast-forward.

3. For each existing target module, read it whole. Check: every old line the proposal removes or replaces (a `-` line, the left side of a `[-…-][+…+]`, a `from:` text) occurs in the file exactly once, character for character. Stop on any line that is missing or occurs twice. The module may have changed since the proposal was written; that is a question, not something to repair.

4. Apply the proposal as written, and only as written. A `+` line is the wanted line without its first two characters; a `-` line leaves; a bare line is unchanged; a `move` takes its text from the `from` module to the `to` module with the marked changes made. A new module is a file with front matter, a `description:` taken from the proposal's `::: description` and `dependencies: []` unless the proposal names them, then a blank line, then the body. Keep every fence as written, its language word included. Do not reword, reorder or tidy any line.

5. Register each new module in `modules.datom`, one entry in the form of its neighbours, `{ { <Kind> <name> Single.<N> } «<kind>/<name>/<N>.md» }`, placed in alphabetical order of the name. A module that holds two versions is `Span.{ A B }`. Check: every path in `modules.datom` exists as a file, and every new module file begins with `---` and a `description:` line. Stop if either fails.

6. Check the diff against the proposal. `git diff --stat` names only the target modules and `modules.datom`; every added line in `git diff` is a `+` line of the proposal and every removed line a `-` line. Check: count the proposal's `+` and `-` lines per module and compare with the diff's added and removed lines; they agree. Stop on any other change.

7. Commit and push. One commit, the message `<module path>: <what changed> (<proposal name>, approved by the living)` and the attribution lines the harness gives for commits. Then `git push origin main`, never forced. Check: `git ls-remote origin refs/heads/main` equals `git log -1 --format=%H`. Stop if the push is rejected; do not rebase, do not retry with force.

8. Bind what the proposal says to bind. A new module is bound to a permaflow only when the order names the permaflows or the module they sit beside; then `flow-meta 'Configure.Amend.{ <Address> Add.PromptModule.<module> }'` for each, a readback by `flow-meta 'Configuration'` counting the module, and the same entries in goldragon-persona `metaflows-0533.datom`, in one commit. Check: the live count and the declared count agree, or the order's known difference is named. Stop on any refusal such as `CurriculumUnavailable`.

9. Tell the page. When the proposal was published as a page, order `{ Psyche core Haiku }` itself, or the publisher the order names, to retitle it in place, title alone, beginning `Purified` when every proposal landed and `Partly purified` when some did not. Do not rebuild or recheck the page.

10. Report Done to the sender of the order: the commit hash, the repository, the modules changed or created, the live and declared counts when step 8 ran, and what was not done. Skills regenerate on their own schedule; say that no flow reads the new text as a skill until they have.

Stop points, as one list: a path outside the named repository, a dirty or non-main tree, a non-fast-forward pull, an old line missing or duplicated, a judgment in the wording, a check that fails, a rejected push, a refused Configure. Ask once, with the question whole.
